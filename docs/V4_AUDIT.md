## 2. 已确认正确的后端边界

### 登录与 JWT

- `AuthService.login` 对不存在邮箱、错误密码和非 `ACTIVE` 用户统一返回 401，不泄露账号是否存在。
- JWT 使用 HS256、固定 issuer、2 小时过期时间。
- `JwtDecoder` 同时校验签名、issuer、有效期，并查询数据库确认用户仍存在且状态为 `ACTIVE`。
- 受保护接口从 JWT subject 取得用户 ID，不接受前端传入 sellerId 或 buyerId。

### 商品与图片

- 更新和下架在 Service 层先校验所有者，并在 SQL 中再次使用 `seller_id` 和 `status='ON_SALE'` 条件更新。
- 商品图片上传/删除会锁定商品行，校验 `sellerId`，预订或售出状态不可修改图片。
- 商品广场查询只返回 `ON_SALE`；卖家可以通过个人中心读取自己的其他状态商品。

### 订单

- 创建订单时以后端 JWT 用户作为买家，禁止购买自己的商品。
- 商品行锁与状态条件更新防止并发重复出售。
- 买入、卖出列表分别按 `buyer_id`、`seller_id` 查询。
- 取消和确认成交只允许订单买家；订单和商品状态在同一事务内更新。

这些逻辑已经存在且设计合理，本阶段不重复实现。

## 3. 新增真实接口验收

`V4MultiUserSecurityIntegrationTests` 使用两个独立注册用户 A、B，通过真实 HTTP 接口验证：

- 不存在账号、错误密码登录失败。
- 畸形 JWT、已过期但签名正确的 JWT、不存在用户的签名 JWT 均不能读取私有数据。
- A 发布并上传图片，B 可以浏览，但不能编辑、下架、上传或删除图片。
- A 可以编辑自己的在售商品。
- B 下单后，A 只能在卖出订单看到该订单，B 只能在买入订单看到该订单。
- 预订中 A 不能编辑、下架或修改图片。
- B 取消后商品恢复在售，A 可以再次编辑。
- B 再次下单并确认成交后商品变为 `SOLD`，不能继续编辑，也不会出现在公开详情中。

实际结果：2 项执行并通过，0 失败、0 错误、0 跳过，`BUILD SUCCESS`。

## 4. 真实发现的前端问题

1. 商品广场打开自己的商品详情时仍显示编辑、下架和图片管理，不符合“广场只负责浏览/购买”的页面职责。
2. 编辑复用发布页面，但返回按钮和保存成功后的跳转固定回商品广场；从个人中心进入时路径不清楚。
3. `app.js` 目前 736 行，认证、API、商品、订单、个人中心和启动逻辑耦合在一个文件中。
4. 验证码发送响应字段实际是 `deliveryMode`，前端却读取 `mode`，真实 SMTP 成功时会显示错误提示文本。
5. 只有接口测试和 JavaScript 语法检查，缺少真实浏览器刷新、退出和跨账号操作验收。

## 5. 后续最小修改范围
