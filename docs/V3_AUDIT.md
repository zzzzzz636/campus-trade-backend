# CampusTrade V3 现状审计

审计日期：2026-10-30  
审计范围：`项目根目录` 的源码、配置、SQL、前端、测试报告、本机服务和 Docker 开发基础设施。本文记录的是 V3 开工时的基线；已处理事项见 `V3_PHASE1.md` 和 `V3_PHASE2.md`。

## 1. 审计结论

CampusTrade V2 已经具备可运行的模块化单体骨架，以及注册、登录、商品发布、图片上传、线下订单状态流转等真实业务代码，不是纯 CRUD 演示。但它目前仍是“经过 H2 自动化验证、部分外部组件真实联调的本地 MVP”，不能把它描述成已经通过 MySQL 生产级验证或已经上线的平台。

V3 首要任务不是重写，而是补齐以下差距：

1. 为现有代码建立真实 Git 基线（审计后已完成）。
2. 将 MySQL 纳入可重复启动和自动迁移流程，并增加 MySQL 关键业务集成测试。
3. 完成商品筛选、排序、编辑、时间信息和更完整的订单展示。
4. 在现有商品详情上增加可降级的 Redis cache-aside 缓存。
5. 接入一个真实但可安全降级的 AI 辅助发布功能。
6. 用真实 MySQL 数据集记录并发与 `EXPLAIN` 结果，不编造性能数字。

## 3. 功能真实性分类

### 3.1 已完成且有自动化测试证据

- 邮箱验证码规则：5 分钟过期、1 分钟发送冷却、5 次错误锁定、成功后删除、防重放。
- 注册、BCrypt 密码、登录、HS256 JWT、JWT 过期与 issuer 校验。
- 用户状态实时校验：账号禁用后，已有 JWT 不能继续访问。
- 商品发布、公开列表、关键词搜索、详情、我的发布和下架。
- JPEG/PNG/WebP 多图上传、魔数校验、大小/数量限制、随机文件名和所有权校验。
- 买家下单、买家取消、买家确认成交、卖家查看收到的订单。
- 商品与订单状态事务一致性，以及重复请求键唯一约束。
- 6 个线程并发购买同一商品时，H2 集成测试中最多成功一个。
- 未登录访问、订单越权、图片越权和部分事务回滚场景。
- Swagger OpenAPI 文档端点。

最近一次完整测试报告为：20 项测试，0 失败，0 错误，0 跳过。该结果包含真实 Redis + Mailpit SMTP 测试，但不包含 MySQL 并发测试。

### 3.2 已有代码，但尚未完成真实环境验证

- `mysql` profile、MySQL Mapper SQL 和三份增量 SQL 已提供；用户已人工执行迁移，但本次审计没有数据库密码，因此未独立读取表结构或执行完整页面验收。

## 4. 架构与代码审查

### 4.1 合理设计

- 代码按 `auth`、`product`、`order`、`category` 业务模块组织，Controller 没有承载主要业务状态流转。
- `OrderService` 使用 `@Transactional` 同时更新订单和商品。
- `ProductMapper.reserveForOrder` 使用 `WHERE status='ON_SALE'` 条件更新，避免先查后改造成的重复预订。
- 取消和完成订单也使用待面交状态条件更新，非法重复操作返回 409。
- JWT 身份来自服务端验证后的 subject，没有从请求体信任用户 ID。
- 图片文件存储通过 `FileStorage` 抽象，可替换为对象存储。
- 上传不信任扩展名和请求 MIME，存储键不使用原文件名。
- Redis Lua 脚本原子完成验证码比较、错误计数和消费删除。

### 4.2 风险与改进项

| 优先级 | 问题 | 风险 | V3 处理建议 |
| --- | --- | --- | --- |
| P0 | 当前不是 Git 仓库 | 无法创建 V3 分支、审查差异或形成可信提交历史 | 经用户确认后初始化 Git，先建立 V2 基线提交，再创建 `feature/v3-resume-readiness` |
| P0 | Docker Compose 无 MySQL | 开发环境不可一键复现，MySQL 数据和账号仍依赖本机手工配置 | 增加带持久化卷和 healthcheck 的 MySQL 服务，同时保留外部 MySQL 配置能力 |
| P0 | 迁移脚本靠人工按顺序执行 | 新环境容易漏表、重复执行 `ALTER` 会失败，无法追踪版本 | 引入 Flyway，从当前实际结构建立基线和后续版本迁移；先备份且不重建现有库 |
| P0 | MySQL 业务闭环未自动验证 | H2 与 InnoDB 的锁、索引和 SQL 语义存在差异 | 增加显式启用的 MySQL 集成测试和可复现说明 |
| P1 | 商品查询只支持关键词 | 无分类、价格、排序，无法满足真实广场体验 | 增加白名单排序、分类和价格参数，DTO 与 Mapper 同步测试 |
| P1 | 没有商品编辑接口 | 用户发布错误后只能下架 | 增加仅卖家、仅 `ON_SALE` 可编辑的条件更新，并处理缓存失效 |
| P1 | DTO 缺少时间和部分展示信息 | 页面无法展示发布时间、订单时间、买卖双方昵称 | 扩充只读响应 DTO，不暴露密码等敏感字段 |
| P1 | 订单幂等键允许为空 | 旧客户端不传时只有并发状态保护，没有请求级防重 | V3 前端继续强制生成；评估新接口是否将其改为必填，保留兼容策略 |
| P1 | 商品详情没有缓存 | 详情是潜在读多写少场景，后续图片和 AI 字段会增加查询成本 | 先度量，再实现短 TTL cache-aside；Redis 故障时回源 MySQL |
| P1 | `server.error.include-message=always` | 未覆盖异常可能向客户端暴露内部信息 | 调整生产配置并补充统一兜底异常处理和日志关联标识 |
| P1 | 商品/订单状态主要靠字符串和业务代码约束 | 非法数据可由手工 SQL 写入 | 在不破坏现有数据前提下评估 CHECK 约束，并集中状态常量/枚举 |
| P2 | `app.js` 集中约 25 KB | 后续筛选、编辑和 AI 功能会显著提高维护成本 | 保持原生技术栈，按 api/auth/products/orders/ui 分模块，不整体迁移 Vue |
| P2 | 图片删除后物理文件清理失败只记录日志 | 可能产生孤儿文件 | 保留事务提交后删除，并增加定期清理/运维说明 |
| P2 | 公开图片按 ID 可长期读取 | 下架图片仍可能被已知 URL 访问 | 明确产品策略；若需私密，读取时关联商品可见性 |
| P2 | 每个 JWT 请求查询一次用户状态 | 安全性好，但用户量上升后增加数据库读取 | 现阶段保留；未来可用短 TTL 状态缓存并设计禁用失效机制 |

## 5. 数据库审查

### 5.1 当前表

- `app_user`：邮箱唯一，保存 BCrypt 密码摘要、昵称、状态和创建时间。
- `category`：名称唯一，提供排序字段。
- `product`：卖家、分类、标题、描述、价格、成色、状态、浏览量、版本和时间字段。
- `product_image`：商品图片元数据，存储键唯一，商品内顺序唯一。
- `trade_order`：商品、买卖双方、成交价格、状态和请求键。

### 5.2 当前索引

- `app_user(email)`：唯一索引来自表约束。
- `product(status, created_at, id)`：支持在售商品按时间倒序列表。
- `product_image(product_id, sort_order, id)`：支持详情图片顺序读取。
- `trade_order(buyer_id, created_at, id)`、`trade_order(seller_id, created_at, id)`：支持个人订单列表。
- `trade_order(buyer_id, request_key)`：请求级重复下单保护。

### 5.3 尚需实测的问题

- `%关键词%` 同时搜索标题和描述不能有效使用普通 B-Tree 索引；先用代表性数据 `EXPLAIN ANALYZE`，再决定是否引入 MySQL FULLTEXT，不提前引入 Elasticsearch。
- 分类、价格与排序加入后，需要按真实组合查询评估复合索引，不能为每个字段机械建索引。
- `product.version` 当前未参与更新，不应在简历中声称已使用乐观锁。
- `view_count` 当前未增加，不应声称已完成浏览量统计。
- 手工 SQL 缺少统一 schema history，V3 应通过迁移工具解决。

## 7. 安全审查

已落实：BCrypt、JWT 签名与 issuer、账号状态检查、DTO 校验、基于登录身份的资源权限、参数化 MyBatis SQL、上传魔数检查、UUID 文件名、路径边界检查、敏感配置环境变量化。

仍需关注：

- 浏览器令牌保存在 `sessionStorage`，需要配合 CSP、输出转义和 HTTPS 降低 XSS 风险。
- Swagger 当前公开，部署环境应根据需要关闭或限制访问。
- 需要为未覆盖异常增加安全的统一响应，避免生产环境暴露内部消息。
- 当前仅验证文件头，不能把它描述为完整恶意内容检测。
- 邮箱验证只证明用户能访问该邮箱，不等于校园身份认证。

## 8. V3 实施顺序

### 阶段 1：真实环境与业务闭环

1. 经确认建立 Git V2 基线和 V3 分支。
2. 引入可回滚、可追踪的 Flyway 迁移方案。
3. 扩展 Compose：MySQL、Redis、Mailpit，使用持久化卷和健康检查。
4. 增加 MySQL profile 的冒烟测试和订单并发测试入口。
5. 在 MySQL 上人工验收注册到成交的完整流程。

验收：应用重启数据保留；迁移可重复应用；MySQL 中并发购买最多一个成功；20 项 V2 回归测试继续通过。

### 阶段 2：网站功能与交互

1. 后端增加分类、价格、排序、分页和时间字段。
2. 实现商品编辑和发布预览。
3. 改造广场、详情、个人中心和订单信息。
4. 将 `app.js` 按职责拆分为原生 ES modules，避免 Vue 整体重写风险。

### 阶段 3：AI 辅助发布

建立独立 `ai` 模块，定义结构化建议 DTO、真实提供商适配器、超时、限流、输入长度校验和禁用/降级配置。没有 API Key 时按钮明确不可用或返回可理解错误，手工发布始终可用。

### 阶段 4：缓存与数据库优化

为商品详情实现 cache-aside，所有商品编辑、图片变化、下架、预订、取消和售出路径统一失效缓存；补充 Redis 故障回源测试。随后基于真实数据记录商品与订单查询的 `EXPLAIN ANALYZE`。

### 阶段 5：测试与交付

完成 MySQL/Redis/AI 测试分层、完整人工演示清单、V3 架构/亮点/测试报告，以及部署条件判断。所有结果只记录实际执行证据。
